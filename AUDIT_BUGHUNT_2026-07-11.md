# Executive Summary — аудит UzGuard (движок + облако)

## 1. Общая оценка риска

Кодовая база находится в состоянии **высокого риска по обоим направлениям сразу**: продукт систематически **пропускает реальные угрозы** (false-negative) и **массово ложно срабатывает на легитимных приложениях** (false-positive) — то есть подводит именно в двух сценариях, ради которых он существует. Ни один из этих провалов не заметен пользователю: движок молча возвращает SAFE или молча вешает DANGER, а облачный слой аутентификации и защита от перебора имеют fail-open дыры. Для sideload-only антивируса без Play-канала это означает, что и защита, и доверие пользователя деградируют одновременно и незаметно.

## 2. Сквозные системные темы

**A. Доверие к атакуемым строкам вместо криптопроверки.** Ключевые сигналы завязаны на подстроки/имена, которые полностью контролирует атакующий:
- `SelfGuard.kt:73` — whitelist «своего» APK по неякорной подстроке `/data/app/` + `/com.uzguard/`; атакующий создаёт такой путь на shared-storage и целиком уходит из скана.
- `InstallShieldService.kt:100` — install-щит пропускает всё с меткой «qalqon»/«uzguard».
- `AccessibilityWatcher.kt:89`, `NotificationAccessWatcher.kt:80` — доверяют подставляемым package-префиксам (`com.google.android.`, `com.miui.`), маскируя вредоносные accessibility/notification-грант.
- `NativeLibAnalyzer.kt:74` — весь нативный анализ пропускается, если `.so` названа `libflutter.so`.
- `CertUtil.kt:35` — отпечаток берётся только у ПЕРВОГО подписанта; multi-signed malware прячет чёрный сертификат вторым.

**B. Мёртвые/обходимые детекторы (false-negative ядра).**
- `DexPatternAnalyzer.kt:77` — needle-паттерны с `;->` НИКОГДА не совпадают с сырыми байтами DEX; SMS/exec/OTP-детекторы мертвы, банкеру недосчитывается до ~130 баллов.
- `LinkScanner.kt:247` — path/query не percent-декодируется; `video%2Emp4%2Eapk` и `/api/upload%5Fsms` проходят как не-DANGER.
- `ApkScanner.kt:925` — Int-усечение `entry.size` (0x80000000) → читается 1 байт DEX → сигнатурный слой пропущен.
- `PermissionCombos.kt:45/46` — комбо переопределены: `READ_SMS+INTERNET` и `RECEIVE_SMS+SEND_SMS` OTP-трояны не ловятся.

**C. Проглатывание исключений = fail-open → false-SAFE.** Системная привычка `catch → SAFE/forward`:
- `ManifestAnalyzer.kt:226` (readBytes-бомба → emptySet → false-SAFE на КАЖДОМ installed-app), `InitialScanActivity.kt:199`, `LinkGuardActivity.kt:63` (открывает вредоносную ссылку), `upload.ts:250`/`login.ts:65`/`format.ts:63` (500 глушит threat-alert). `GuardWorker.kt:211` вдобавок глотает `CancellationException`.

**D. FP-флуд, обходящий trust-shield (тот же класс, что уже «чинили»).** Hard-DANGER short-circuit'ы срабатывают ДО проверки доверия:
- `FilenameHeuristic.kt:314` — `payment`→`payme`, `clicker`→`click` → мгновенный DANGER даже на подписанном легит-приложении (bypass shield на `ApkScanner.kt:1092` до `:1141`).
- `ApkScanner.kt:1464` — `droppedSo`/`encrypted` TIER-1 выше trust-shield → упакованный легит-банк = malware.
- `RemoteConfig.kt:227` — у порогов нет нижней границы; подписанный конфиг с `danger=0` → всё DANGER.
- `BankAppAudit.kt:94/102/114` — четыре разных дефекта: и легит sideload-банк с ОФИЦИАЛЬНЫМ сертификатом помечается фейком, и троян на «мёртвом» package банка не проверяется вовсе.

**E. Concurrency: неатомарный read-modify-write SharedPreferences.** `ScanHistory.kt:47`, `ThreatActions.kt:47`, `Quarantine.kt:125`, `NotificationHelper.kt:177` (фикс. ID 777) — при параллельных сканах теряются записи истории, action-токены, элементы карантина и сами алерты о втором вредоносном APK.

**F. «Успех», которого не было (delete/update-ложь).** `CommandRouter.kt:112` — Telegram-delete проверяет `!file.exists()` раньше sandbox-owner, обходит закалённый `FileDeleter` и заново вводит документированный баг #delete-false-success. `SelfUpdate.kt:145` — background-launch install молча дропается на Android 10+, возвращает «OK» → устройство без патча.

**G. Self-kill как availability-DoS.** `SecurityGuard.kt:512` (`test-keys`/`unknown` → emulator-kill бут-луп на серых/кастом-ROM устройствах узбекского рынка) и `SecurityGuard.kt:48` (Play-переподпись → kill на 100% Play-инсталлов) — вооружённый механизм убийства процесса на слабых индикаторах.

**H. Облачная аутентификация fail-open.** `ratelimit.ts:49` — любая ошибка Supabase полностью снимает защиту от перебора master-credential; `login.ts:65` — 500 до `recordFailure` не считается попыткой; `[id].ts:198` — legacy shared-secret (по умолчанию включён, извлекаем из APK) → poisoning ростера и подмена PII; `app.py:94` — API-ключ в query-string течёт в логи; `TelegramBot.kt:323` — первый `/x` в группе захватывает управление устройством.

**I. Тепло/батарея (хронический класс проекта).** `CloudTelemetry.kt:405` (активный GPS-fix до 8с на КАЖДЫЙ upload, включая SAFE), `GuardWorker.kt:122` (нет `isStopped`), `InstalledAppsRescanWorker.kt:150` (нет thermal-constraint), `AnimationHelper.kt:91`/`NewsTickerAdapter.kt:79`, `MainActivity.kt:528` (реэнтрант-волны сканов).

## 3. Самый срочный фикс

**`DexPatternAnalyzer.kt:77` — восстановить рабочее сопоставление DEX-паттернов (не искать contiguous `;->` в string-pool).** Это не просто баг, а тихий отказ основного детектирующего сигнала: SMS-стилеры и банкеры (ровно семейство Ajina.Banker, против которого продукт и создавался) недобирают до ~130 баллов и уходят ниже порога DANGER, помечаясь как SAFE. Пользователь при этом видит «всё чисто». Антивирус, который молча не детектирует свою профильную угрозу, хуже отсутствия антивируса — поэтому чинить в первую очередь.

Непосредственно следом (co-critical, тот же спринт): `FilenameHeuristic.kt:314` (FP-флуд на обычных именах файлов, разрушает доверие) и `SecurityGuard.kt:512` self-kill (бут-луп на реальных устройствах целевого рынка). Первый — «не видит зло», два вторых — «наказывает добро»; вместе они закрывают обе стороны провала.

### 1. [HIGH] `CommandRouter.kt:112` — Telegram remote-delete bypasses FileDeleter and lies "Fayl allaqachon yo'q" for /Android/data sandbox malware

- **Файл:** `ApkGuard/app/src/main/java/com/kiberqalqon/CommandRouter.kt:112`  ·  **Группа:** filedeleter-actions  ·  **Категория:** false-success-honesty  ·  **Confidence:** high
- **Сценарий отказа:** A threat report is registered (CommunityReportClient.register -> ThreatActions) for an APK whose path is inside a sandboxed dir, e.g. /storage/emulated/0/Android/data/org.telegram.messenger/files/x.apk. Owner taps the inline 🗑 Delete button in Telegram. handleDelete does File(entry.apkPath) then checks `!file.exists()` FIRST. On Android 11+, a third-party app cannot stat another app's /Android/data sandbox, so file.exists() returns false even though the malware is still physically present. The handler then replies "✅ Fayl allaqachon yo'q ... Qurilmada bu fayl topilmadi" and removes the token. This is exactly the documented #delete-false-success bug that FileDeleter.delete() was hardened against (sandboxOwner() check placed ABOVE its own !file.exists()), but the remote/Telegram delete path never calls FileDeleter and re-introduces the lie: owner is told the malware is gone while it survives in the owner-app sandbox.
- **Фикс:** In handleDelete, mirror FileDeleter honesty: call FileDeleter.sandboxOwner(file) (or route the delete through FileDeleter) BEFORE the !file.exists() short-circuit. If sandboxOwner != null, reply honestly that the file lives in another app's sandbox and cannot be removed remotely (offer the in-app / delete-the-Telegram-message path) instead of claiming it is already gone.
- **Вердикт верификатора:** The remote Telegram delete handler (CommandRouter.handleDelete, lines 111-132) bypasses FileDeleter and does bare File(entry.apkPath) + !file.exists() + file.delete(), reintroducing the documented #delete-false-success lie for Telegram-shared sandbox malware. Concrete reachable path: ShareReceiverActivity.copyToCache copies a Telegram-shared APK to cacheDir/shared/x.apk and scans THAT copy (apk_is_copy=true, origin URI passed only to the on-device Activity). ApkScanner.scan→CommunityReportClient.reportThreat registers the CACHE-COPY path in ThreatActions, whose Entry stores only token/apkPath/apkName/verdict (ThreatActions.kt:29-35) — no isCopy/originUri flag. So when the owner taps 🗑 in Telegram, handleDelete either (a) deletes the cache copy and replies "🗑 O'chirildi" while the real virus survives in Telegram's /Android/data sandbox, or (b) finds the copy already evicted (cacheDir is routinely cleared), hits !file.exists(), and replies line 115 "✅ Fayl allaqachon yo'q … Qurilmada bu fayl topilmadi" — again while the original survives. Both are false-success lies delivered by the exact flagged code, and both differ from the honest on-device path (AutoScanActivity knows apkIsCopy/originUri; FileDeleter.delete puts sandboxOwner() ABOVE !file.exists()). The claim's precise stat-on-/Android/data mechanism is imprecise (inaccessible sandbox files can't be scanned to DANGER, so the registered path is the cache copy, not the raw sandbox path), but the flagged lines, the reachable failure, and the security outcome — owner told malware is gone while it survives in the owner-app sandbox — are all real. Severity HIGH: it re-creates a bug the team explicitly hardened against and actively misinforms the owner, though reachability is gated behind community-share consent + DEV_TG config + use of the owner-only remote delete button (the common on-device path stays honest).

### 2. [HIGH] `DexPatternAnalyzer.kt:77` — Method-reference patterns using ";->" never match raw DEX bytes (dead SMS/exec/OTP detectors)

- **Файл:** `ApkGuard/app/src/main/java/com/kiberqalqon/DexPatternAnalyzer.kt:77`  ·  **Группа:** dex-dropper  ·  **Категория:** false-negative  ·  **Confidence:** high
- **Суть:** analyze() reads raw classes*.dex bytes and does text.contains(needle) over an ISO-8859-1 decoding of the string pool. But a raw DEX file stores each string SEPARATELY: a type descriptor (e.g. Landroid/telephony/SmsManager;) is one string_data entry and a method name (e.g. sendTextMessage) is a different, non-adjacent entry. Method references are index triples, not literal text. The smali-style concatenation `Lclass;->method` only exists in baksmali output, never as contiguous bytes in a DEX. Therefore every needle containing ";->" can never be found. This silently disables the highest-value detectors: sendTextMessage (35), sendMultipartTextMessage (35), Runtime;->exec (25), AccessibilityEvent;->getText / AccessibilityNodeInfo;->getText (25/20, OTP grabbers), getSubscriberId/getSimSerialNumber/getDeviceId (IMEI/IMSI stealers), isDebuggerConnected. These are exactly the SMS-interception + OTP-grabbing signatures that define Uzbek banking malware (Ajina.Banker), so the score contribution from them is always 0.
- **Сценарий отказа:** An SMS-stealer DEX that calls android.telephony.SmsManager.sendTextMessage contains the string "Landroid/telephony/SmsManager;" and the string "sendTextMessage" separately in its string pool. The needle "Landroid/telephony/SmsManager;->sendTextMessage" is never present as contiguous bytes, so text.contains() returns false, the 35-point SMS signal is never added, and the malware's DEX score is understated by up to ~130 points (all ;-> needles), letting a banker slip below the DANGER threshold.
- **Фикс:** Match the type descriptor and method name independently instead of the concatenated smali form. Either split each pattern into two needles that must BOTH be present in the same dex (e.g. text.contains("Landroid/telephony/SmsManager;") && text.contains("sendTextMessage")), or drop the class prefix and match the bare method-name string where it is distinctive (e.g. "sendMultipartTextMessage", "getSubscriberId"). Do NOT keep any needle containing ";->".
- **Вердикт верификатора:** The bug is real and provable from DEX format. analyze() reads raw classes*.dex bytes (L157-174) and does text.contains(pattern.needle) over an ISO-8859-1 decode of the string pool. In a real DEX, strings live in string_data_item as separate length-prefixed MUTF-8 entries each terminated by 0x00; type descriptors (Landroid/telephony/SmsManager;) and method names (sendTextMessage) are distinct, non-adjacent entries, and method calls are resolved via method_id_item index triples, never as literal Class;->method text. The `->` arrow is smali display syntax only, so any needle containing ;-> can never appear as contiguous bytes — not even across a boundary, since ; is always followed by 0x00, not -. This makes these detectors permanently dead: Runtime;->exec (25), getDeviceId (8), getSubscriberId (10), getSimSerialNumber (10), sendTextMessage (35), sendMultipartTextMessage (35), isDebuggerConnected (5), AccessibilityEvent;->getText (25), AccessibilityNodeInfo;->getText (20) — ~173 points that always contribute 0. These are exactly the SMS-send + OTP-grabber signals of Ajina.Banker. The author's comments (L9/L20-22) confirm the misconception that method refs are plain text; the method NAME alone is in the pool (a bare `sendTextMessage` needle would match), but the concatenation is not. Not refuted by the score<=0 skip (affected needles have positive scores) nor by ISO-8859-1 (byte content unchanged). Downgraded from CRITICAL to HIGH because corroborating non-arrow needles still fire — SMS_RECEIVED (20), SMS_DELIVER (25), abortBroadcast (15), TYPE_APPLICATION_OVERLAY (12), api.telegram.org/bot (25), packer/frida/magisk/TracerPid strings — so a banker is understated, not wholly invisible, and DexPatternAnalyzer is one of several ApkScanner analyzers.

### 3. [HIGH] `FilenameHeuristic.kt:314` — Typosquat check flags common words (payment, clicker, signed) as brand impersonation → immediate hard DANGER on legit apps

- **Файл:** `ApkGuard/app/src/main/java/com/kiberqalqon/FilenameHeuristic.kt:314`  ·  **Группа:** obf-filename  ·  **Категория:** false-positive  ·  **Confidence:** high
- **Сценарий отказа:** A legitimate APK named 'payment_receipt.apk' (or any file/installed app whose tokenized name contains 'payment', 'clicker', 'signed', etc.) with a package not starting with the brand prefix. In matchBrand(), the typosquat loop tests token 'payment' (len 7) against brand 'payme' (len 5): it is inside the window (brand.length-1)..(brand.length+2) = 4..7, and levenshtein('payment','payme',2) = 2 (two trailing deletions) → returns ('typosquat','payment'). analyze() then sets brandHit=BrandImpersonation and returns it as hardDanger. ApkScanner.kt:1092-1110 turns any BrandImpersonation hardDanger into an immediate DANGER verdict, and this runs BEFORE the VERIFIED/trust-shield check at ApkScanner.kt:1141 — so even a signature-verified legit app is force-flagged DANGER. Same false positive fires for 'clicker'→'click', 'signed'→'signal', etc. This is exactly the false-positive-flood class the trust shield was added to prevent, but the hard-DANGER short-circuit bypasses it.
- **Фикс:** Do not treat a token as a typosquat when the only edits are appending/removing a common word suffix (e.g. brand+'ment', brand+'er', brand+'s', brand+'ing'), or gate typosquat behind a small common-word dictionary check so real words like 'payment'/'clicker'/'signed' are excluded. Also consider narrowing the length window to brand.length-1..brand.length+1 for insertions plus the dictionary guard. At minimum, feed the brandHit through the trust/VERIFIED shield instead of returning DANGER before it.
- **Вердикт верификатора:** Concrete failure path verified end-to-end. Tokenizer (FilenameHeuristic.kt:227) turns 'payment_receipt.apk' into tokens {payment, receipt}. In matchBrand (305-318), brand='payme' (len 5): exact fails, matchConcatenatedBrand correctly rejects it (after-char 'n' is lowercase → afterOk=false, per the guard comment at 321-323), BUT the typosquat loop at 311-316 has no word-boundary guard: 'payment' len 7 ∈ window 4..7 and levenshtein('payment','payme',2)=2 → returns ('typosquat','payment'). matchedToken is not in OWN_BRANDS (line 235), so for any package not starting with uz.dida.payme, pkgOk=false → brandHit=BrandImpersonation, hard set. The same fires for 'clicker'→'click' (auto-clicker apps, extremely common), 'signed'→'signal' ('signed.apk'), etc. In ApkScanner.kt the hard-danger when-block (1092-1127) does an unconditional return finalizeResult(...Verdict.DANGER...) on BrandImpersonation, which executes BEFORE verifiedTrusted (line 1141) and decideVerdict — so a signature-VERIFIED legit app is still force-flagged DANGER, defeating the trust shield. The concat path's own comment claims 'payment'/'clicker' are NOT matched, but the typosquat fallback shadows that guard. Realistic, common filenames trigger it; severity HIGH is appropriate (hard-DANGER FP on legit apps, bypassing all trust mitigations). Not CRITICAL only because it requires the filename to tokenize to a word within Levenshtein-2 of a ≥5-char brand and a mismatched package, not literally every app.

### 4. [HIGH] `ImprovedApkFileObserver.kt:32` — Global debounce(700) drops all-but-last APK when several land in one folder within 700ms

- **Файл:** `ApkGuard/app/src/main/java/com/kiberqalqon/ImprovedApkFileObserver.kt:32`  ·  **Группа:** file-observers  ·  **Категория:** detection-bypass-false-negative  ·  **Confidence:** high
- **Сценарий отказа:** All CREATE/MOVED_TO/CLOSE_WRITE events for a given watched folder feed a single SharedFlow, and `.debounce(700)` emits only the LATEST value after 700ms of silence. If two (or more) distinct APKs arrive in the same folder inside a 700ms window — e.g. Telegram/WhatsApp finishing two downloads back-to-back, a bulk save, or a benign file arriving right before a malware APK — debounce keeps only the last File and silently discards the earlier one(s). The dropped APK is never passed to waitUntilStable/onApkReady, so it gets NO real-time scan/popup/telemetry. debounce here is meant to coalesce the multiple events of the SAME file, but because it operates across the whole flow it cannot distinguish per-file, so it also coalesces DIFFERENT files. A malicious APK can slip past real-time detection simply by being delivered alongside another file. Only the 30-min GuardWorker backstop would catch it later.
- **Фикс:** Debounce/stabilize per-file, not globally. e.g. key the flow by absolute path and debounce within each key (flatMapMerge over groups, or maintain a per-path Job map that restarts a 700ms stabilization timer), so each distinct APK is processed independently instead of the burst collapsing to one.
- **Вердикт верификатора:** Verified mechanism is real. In ImprovedApkFileObserver.kt, onEvent() tryEmit()s every CREATE/MOVED_TO/CLOSE_WRITE File into one per-observer SharedFlow (line 26), and the init collector applies `.filter{apk}.debounce(700)` (lines 30-33). Kotlinx `Flow.debounce` is not per-key: on each emission it restarts the 700ms timer and ultimately emits only the LATEST File. MultiPathFileObserver.kt:70 creates one observer per folder, so within a single watched folder two distinct .apk files whose events fall inside a 700ms window collapse to only the last; the earlier File never reaches waitUntilStable/onApkReady (lines 35-37), so it gets no real-time scan/popup/reportDownloadDetected telemetry. Concrete path: File A MOVED_TO at t=0, File B MOVED_TO at t=150ms → single debounced emit of File B, File A dropped. So the bug exists as described. Severity lowered from HIGH to MEDIUM: this degrades only the real-time download layer, not overall detection — the dropped APK is still caught at install time by PackageInstallReceiver/ShareReceiver (per the project's own model, install-time is the primary defense; folder-watch is best-effort) and by the periodic GuardWorker folder rescan. The trigger is also narrow: both files must be .apk, in the same folder, with events under 700ms apart, which is atypical for real sequential user downloads.

### 5. [HIGH] `InstallShieldService.kt:100` — Install shield skips any app whose label contains "qalqon"/"uzguard" — trivial impersonation bypass

- **Файл:** `ApkGuard/app/src/main/java/com/kiberqalqon/InstallShieldService.kt:100`  ·  **Группа:** a11y-install-shield  ·  **Категория:** detection-bypass  ·  **Confidence:** high
- **Суть:** Own-app exemption uses attacker-controllable display label with substring matching.
- **Сценарий отказа:** A malicious APK is labeled "Kiber Qalqon Update" or "UzGuard Pro" (a common typosquat tactic for security apps). At line 62 onAccessibilityEvent calls isOwnAppLabel(label) and returns before shouldBlock() is ever reached, because isOwnAppLabel does substring matching on "uzguard"/"kiberqalqon"/"qalqon". The install-confirm dialog is therefore never auto-cancelled even when the sample was just flagged DANGER, and the whole third-rubezh install shield is defeated by choosing an app name.
- **Фикс:** Do not identify 'own app' by display-label substring. Match the installer target by package name against BuildConfig.APPLICATION_ID / namespace (and the .debug variant), or verify the signing cert, instead of a fuzzy label contains(). At minimum drop the broad "qalqon" token which collides with many legit/hostile names.
- **Вердикт верификатора:** Verified in InstallShieldService.kt. Line 61-62: guessAppLabel() reads the app's display label from the installer dialog's visible text, then isOwnAppLabel(label) causes an early return BEFORE shouldBlock() at line 64. isOwnAppLabel (lines 98-100) does pure substring matching on the attacker-controllable display label (contains "uzguard"/"kiberqalqon"/"qalqon") with no package-name or signature verification. Concrete bypass: a malicious APK labeled "Kiber Qalqon Update" or "UzGuard Pro" — even one just flagged DANGER (so shouldBlock would return true via InstallApproval.isDanger / hasRecentDanger) — matches isOwnAppLabel, so the auto-cancel never executes and the install shield is defeated purely by choice of app name. "qalqon" (shield) is a very common Uzbek word and a documented typosquat vector for this app family, so the failure path is trivially reachable, not contrived. The correct exemption should key on installing package + signing cert, not the label.
